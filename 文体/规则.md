# 写规则 · 一眼看出多硬

先读核心规范 [规范.md](../规范.md),尤其是第四节能愿动词。下面只写规则类多出来的规矩。

起因(2026-10-06):让子代理用两种读法(按字面读、按执行者读)各读一遍 coding-style.md 和 testing.md,给 40 条规则逐条判强度(硬 / 默认 / 可选 / 判断不了)。结果 9 条两遍判得不一样,4 条判断不了。大部分规则句里根本没有义务词,强度只能靠标题和上下文猜。比如「在系统边界验证输入」一遍判默认、一遍判硬;「Iron Law: no production code without a failing test first」字面是硬的,但另一条又说跟减法阶梯冲突时以阶梯为准。另外,93 份规则和反馈记忆里,表示「禁止」的说法有 9 种。
这次只证明了规则的强度读不准,还没找到因此执行错的实例。下面的规矩照 GB/T 1.1-2020 的能愿动词、EARS 需求句式和 RFC 2119。

## 下笔时

- **文件开头放一句图例。** 照 RFC 2119 要求的固定声明来写:「本文件的义务词照 GB/T 1.1-2020:应 / 不应 = 必须做到,任何情况都不能违反;宜 / 不宜 = 默认这样做,有理由可以不做,但要说出理由;可 / 不必 = 做不做都行。」2026-10-06 实测:同一份改写稿,没有图例时,读者看不出「应」到底有多硬(19 条里 5 条两遍判得不一样,4 条判断不了);加上图例以后,20 条全部判得一致。
- **每条规则带一个义务词,四档选一档。** 要求用「应 / 不应」,推荐用「宜 / 不宜」,允许用「可 / 不必」,能力用「能 / 不能」。不用「必须、一律、绝不、务必、禁止、不准、不许」,也不用「Never / ALWAYS」;想表达的硬度,用档位说。
- **「应」要少用。** 只给真的不能违反的规则(RFC 2119 第 6 节)。拿不准的就用「宜」,写清什么情况可以不做。
- **触发条件写在前面。** 照 EARS:「当〈触发〉时,〈谁〉应〈做什么〉」「如果〈不想要的情况〉,〈谁〉应〈怎么处理〉」。「3+ failed fixes = stop」改成「同一个问题修了 3 次还没好时,应停下来重新看设计」。
- **一条规则一件事。** 一句里塞两个要求,就拆成两条。
- **写清为什么。** 一句理由加一个出处(哪天、谁说的、哪次事故)。没有理由的规则,执行的人在边界上没法判断。
- **冲突事先说清。** 两条规则可能打架时,在其中一条里写明「与某某冲突时,以某某为准」,别让执行的人现场选。
- **改旧规则时只改用词,不改意思。** 如果原文本来就看不出多硬,按最弱的理解写成「宜」,并在那条后面标「〔强度待作者定〕」。
