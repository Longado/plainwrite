# EARS 需求句式 和 INCOSE 需求写作指南

## 是什么

- EARS(Easy Approach to Requirements Syntax)是劳斯莱斯的 Mavin 等人 2009 年提出的需求写法：用几种固定句式，逼写的人把触发条件写出来。
- INCOSE(国际系统工程协会)的《需求写作指南》列了一套写需求的规则。

## 来源和可信度

- EARS：句式来自维基百科条目 https://en.wikipedia.org/wiki/Easy_Approach_to_Requirements_Syntax ，Mavin 等人的原论文未读。
- INCOSE：第 4 版(2023)的 PDF 未打开，下面只列搜索摘要里能对上的几条，规则总数和分类未核实。

## 要点

EARS 的五种句式(中文是我们的译法)：

| 类型 | 句式 |
|---|---|
| 普适 | 〈系统〉应〈响应〉 |
| 事件驱动 | 当〈触发〉时，〈系统〉应〈响应〉 |
| 状态驱动 | 在〈状态〉期间，〈系统〉应〈响应〉 |
| 可选功能 | 在包含〈功能〉的情况下，〈系统〉应〈响应〉 |
| 不想要的情况 | 如果〈触发〉，那么〈系统〉应〈响应〉 |

几种句式可以组合使用。

INCOSE(二手)：句子结构完整；用主动语态；不用含糊词；不留「如有必要」这类给自己开脱的条款；不写「包括但不限于」这类开放式条款；一条需求只写一件事。

## plainwrite 怎么用

| 条目 | 状态 | 在哪 |
|---|---|---|
| 触发条件写在前面 | 已收 | `文体/规则.md`：「当……时，……应……」，例子是把「3+ failed fixes = stop」改写一遍 |
| 一条只写一件事 | 已收 | `文体/规则.md`「一条规则一件事」 |
| 五种句式全套用 | 不收 | 规则文件不是需求规格书，句式只借思路 |
| 含糊词、开脱条款的词表 | 暂不收 | 没有实例证明我们写规则时犯这个毛病；以后要收，先拿 `工具/backtest.py` 回测 |
